Hardware integration

The same pipeline on the real TurtleBot3 Waffle Pi and what had to change

1. Our approach: change the robot layer, and keep the algorithms the same

hardware_integration/run_hardware.py runs the explore mission on the real robot through rosbridge, using the UTS-RI turtlebot_rosbridge API (a read-only git submodule). Perception, estimation and control are the same modules as in simulation:

  • Perception: LiDAR walls and obstacles, and ArUco range and bearing.
  • Estimation: MarkerSLAM, localising from the reference marker with the wall-line heading.
  • Control: Navigator with the LiDAR grid, A* and spline, LQR path following, Week 9 docking, find and back off.

The only new implementation is the robot layer around them. Robot side: ROS2 Humble, TURTLEBOT3_MODEL=waffle_pi, LDS-01 on /scan, camera_ros at 640×480, and /joint_states, /odom and /cmd_vel, with rosbridge on port 9090.

2. Changes made from the simulation code

The mission itself

The original "route" mission knew its start pose, the full marker map and a fixed route, however none of these exist on a real robot dropped into a room. We rebuilt it as the explore mission. The robot localises from whichever reference marker it can see, finds the dock from one measured offset, maps obstacles with its LiDAR as it drives, and replans (D, C). The route mission is kept as the baseline for comparison and evidence.

A watchdog stops the robot if odometry or LiDAR data is more than 0.5 s old.

Timing

  • In simulation the loop is stepped, but on hardware it must keep up with the wall clock. Processing a LiDAR scan dominates so RANSAC uses 150 hypotheses per wall instead of 500. With about 350 points, and walls holding a large share of them, 150 still finds each wall almost surely, at under a third of the cost. On the simulated stand-in, loops took 21 ms on average, 60 ms at the 95th percentile and 96 ms at worst, against a 50 ms budget.
  • The scan and the camera frame are no longer taken at the same instant, and one scan takes 0.2 s to sweep. So the wall-line heading update is only used while the robot turns slower than 0.2 rad/s.

Camera calibration on the real camera

The simulated lens has no distortion so simulation uses a pinhole model (B). A real lens does have distortion, so calibrate_camera.py fits the full (k1, k2, p1, p2, k3) model, and the pipeline undistorts every frame before using the pinhole model as in simulation.

Procedure: intrinsic calibration from the robot's own camera (Week 3 B, C), with the printed checkerboard held in front of the robot at varied distances (0.4–1.2 m), positions across the image, and tilts of up to about 40°. This gives the real camera's focal length, principal point and lens distortion, so marker ranges and bearings are computed with the real camera's intrinsics rather than the simulated camera's. Each TurtleBot in the lab had a different camera and mounting, so the calibration was repeated for the robot in use (see Porting issues). The saved calibration (30 October 2026) used 17 views:

A main issue/caveat within our testing: A k3 of −17.5 and a principal point 68 px above the image centre are both typical signs of an over-fitted calibration, for example one where the board did not reach the image corners. In simulation, the same pattern (large distortion terms the data did not support) made the principal point 5–10× less repeatable. If marker ranges disagree with a tape measure, this calibration is the first thing to redo.

4. Results on the real robot

Trials tested - seen in videos below

  • Multiple obstacle configurations, and placing the markers at different points. Confirmed that the pipeline was robust enough to handle multiple test setups.
  • A random, sudden obstacle that appears in its path - placing a foot/leg directly in the path of the robot, it was still able to replan around the new obstacle and dock. This repeats the simulation's obstacle_appears robustness scenario (E) on hardware: a team member stepped in front of the robot while it was driving, the LiDAR sensed the obstacle, and the robot replanned its path around it.

Overall: docked in 4 of 5 runs, with a mean mission time of about 80 s. "Docked" is the robot's own test, as in simulation: the camera reads the dock marker within 10 mm of the docking distance, and centred. On hardware the docking distance is 0.4 m from the dock marker, against 0.25 m in simulation, because closer than that the camera can no longer read the whole marker (issue 2). We did not measure the docked pose against a ruler, so there is no hardware equivalent of the simulation's true docking error.

The run that did not dock stopped short of the dock and never moved again. In that run the LiDAR safety corridor still had the simulation's size: 0.203 m either side and 0.286 m ahead of the robot's origin, reaching up to 0.35 m at its front corners. That is further than the clearance the planner keeps from obstacles (0.28–0.30 m). On the smaller real track, planned paths passed obstacles inside that gap, so the safety stop halted the robot on a path the planner considered safe, and replanning from inside the planner's margin found no route. After that run we narrowed the corridor to 0.183 m and 0.186 m (hw_config.py), so it now reaches at most 0.26 m, inside the planner's clearance. The simulation's larger room never exposed this mismatch: the explore mission there was 130/130 (E). The general lesson is that the safety check must never reach further than the planner's clearance.

5. Porting issues

The transition from simulation to hardware was mostly seamless: the perception, estimation and control code ran unchanged, and we came across few bugs. The two main issues both came from the real camera's delayed response and limited field of view, which the simulated camera does not have.

  1. Spinning too fast to see the reference marker. The mission starts by turning on the spot at a set angular velocity until the reference marker is in view (search mode, D). On the robot, the camera never registered the marker: it was spinning too fast for a camera whose frames arrive with a delay the simulated camera does not have, so the marker had already left the view by the time a frame was processed. The fix was simple, slowing the turn: commands on hardware are capped at W_LIMIT = 0.4 rad/s (from 1.0), so the search turn (0.7 rad/s in simulation) runs at 0.4 rad/s. Working out why it was happening took longer than the fix.
  2. Markers too high and too small for the camera's field of view close up. We first printed the markers at 100×100 mm and mounted them about 175 mm off the ground. Close to a marker, the camera's limited field of view could no longer see the whole marker, so it could not be detected. Without it, the robot lost track of where it was on the track and moved away from the dock. The markers are now mounted with their centres 0.12 m above the floor (MARKER_HEIGHT), and docking stops with the camera 0.4 m from the dock marker (DOCK_DISTANCE; 0.25 m in simulation), where the whole marker stays in view.

Smaller issues:

  • A different camera on each robot. The TurtleBots in the lab had different camera models and mountings, and some suffered more from lighting or motion blur because of camera quality. Each time we changed robot, we had to recalibrate the camera.
  • Markers must be mounted upright, or the camera does not recognise them.
  • The calibration board and markers differ from simulation (25 mm squares, 0.1 m markers), so these values moved out of the shared configuration into hw_config.py. That way, tuning the real robot cannot change the simulation results.

6. To run it

git submodule update --init
python -m pip install --no-deps -e "./external/turtlebot_rosbridge"
python -m pip install "roslibpy>=2.0,<3" "pynput>=1.7"

python hardware_integration/check_sensors.py 192.168.1.2XX                       # topics, no motion
python hardware_integration/calibrate_camera.py 192.168.1.2XX                    # writes camera_calibration.json
python hardware_integration/run_hardware.py 192.168.1.2XX --dry-run --show-camera  # localise and plan, no motion
python hardware_integration/run_hardware.py 192.168.1.2XX --show-camera --video runs/run1.mp4 --log runs/run1.pkl
python hardware_integration/run_hardware.py --sim                               # the MuJoCo stand-in

--no-deps matters: the API asks for opencv-python, which would overwrite opencv-contrib-python 4.10 (both install into the same cv2 folder). Full instructions: hardware_integration/README.md.
