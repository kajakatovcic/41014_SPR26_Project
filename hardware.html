Hardware integration

The same pipeline on the real TurtleBot3 Waffle Pi and what had to change

1. Our approach: change the robot layer, and keep the algorithms the same

hardware_integration/run_hardware.py runs the explore mission on the real robot through rosbridge, using the UTS-RI turtlebot_rosbridge API (a read-only git submodule). Perception, estimation and control are the same modules as in simulation:

  • Perception: LiDAR walls and obstacles, and ArUco range and bearing.
  • Estimation: MarkerSLAM, localising from the reference marker with the wall-line heading.
  • Control: Navigator with the LiDAR grid, A* and spline, LQR path following, Week 9 docking, find and back off.

The only new implementation is the robot layer around them. Robot side: ROS2 Humble, TURTLEBOT3_MODEL=waffle_pi, LDS-01 on /scan, camera_ros at 640×480, and /joint_states, /odom and /cmd_vel, with rosbridge on port 9090.

2. Changes made from the simulation code

The mission itself

The original "route" mission knew its start pose, the full marker map and a fixed route, however none of these exist on a real robot dropped into a room. We rebuilt it as the explore mission. The robot localises from whichever reference marker it can see, finds the dock from one measured offset, maps obstacles with its LiDAR as it drives, and replans (D, C). The route mission is kept as the baseline for comparison and evidence.

A watchdog stops the robot if odometry or LiDAR data is more than 0.5 s old.

Timing

  • In simulation the loop is stepped, but on hardware it must keep up with the wall clock. Processing a LiDAR scan dominates so RANSAC uses 150 hypotheses per wall instead of 500. With about 350 points, and walls holding a large share of them, 150 still finds each wall almost surely, at under a third of the cost. On the simulated stand-in, loops took 21 ms on average, 60 ms at the 95th percentile and 96 ms at worst, against a 50 ms budget.
  • The scan and the camera frame are no longer taken at the same instant, and one scan takes 0.2 s to sweep. So the wall-line heading update is only used while the robot turns slower than 0.2 rad/s.

Camera calibration on the real camera

The simulated lens has no distortion so simulation uses a pinhole model (B). A real lens does have distortion, so calibrate_camera.py fits the full (k1, k2, p1, p2, k3) model, and the pipeline undistorts every frame before using the pinhole model as in simulation. The saved calibration (30 October 2026) used 17 views:

Reprojection RMS0.503px
f / ρu, f / ρv1336.0px, 1342.0px
Principal point(321.4, 171.6)px
Distortion (k1, k2, p1, p2, k3)(0.2107, 1.2261, −0.0383, −0.0005, −17.4953)

A main issue/caveat within our testing: A k3 of −17.5 and a principal point 68 px above the image centre are both typical signs of an over-fitted calibration, for example one where the board did not reach the image corners. In simulation, the same pattern (large distortion terms the data did not support) made the principal point 5–10× less repeatable. If marker ranges disagree with a tape measure, this calibration is the first thing to redo.

4. Results on the real robot

Trials tested - seen in videos below

  • Multiple obstacle configurations, and placing the markers at different points. Confirmed that the pipeline was robust enough to handle multiple test setups.
  • A random, sudden obstacle that appears in its path - placing a foot/leg directly in the path of the robot, it was still able to replan around the new obstacle and dock.

5. Porting issues

Recorded during bring-up:

  • Markers must be mounted upright, or the camera does not recognise them.
  • Close to the dock, the camera lost the marker. The docked distance on hardware is 0.4 m against 0.25 m in simulation.
  • The calibration board and markers differ from simulation (25 mm squares, 0.1 m markers), so these values moved out of the shared configuration into hw_config.py. That way, tuning the real robot cannot change the simulation results.
  • Camera issues: Camera models differed between the TurtleBot models available, and some suffered more lighting or motion blur issues due to camera quality. Mounting was also different per model, meaning each time we had to recalibrate the camera.

6. To run it

git submodule update --init
python -m pip install --no-deps -e "./external/turtlebot_rosbridge"
python -m pip install "roslibpy>=2.0,<3" "pynput>=1.7"

python hardware_integration/check_sensors.py 192.168.1.2XX                       # topics, no motion
python hardware_integration/calibrate_camera.py 192.168.1.2XX                    # writes camera_calibration.json
python hardware_integration/run_hardware.py 192.168.1.2XX --dry-run --show-camera  # localise and plan, no motion
python hardware_integration/run_hardware.py 192.168.1.2XX --show-camera --video runs/run1.mp4 --log runs/run1.pkl
python hardware_integration/run_hardware.py --sim                               # the MuJoCo stand-in

--no-deps matters: the API asks for opencv-python, which would overwrite opencv-contrib-python 4.10 (both install into the same cv2 folder). Full instructions: hardware_integration/README.md.
