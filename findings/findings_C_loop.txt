====================================================================================================
1. END-TO-END LOOP (main.py)
====================================================================================================

1.1 Structure
  simulation -> sensor drivers -> perception -> estimator -> controller -> unicycle_to_wheels() -> MuJoCo
- Each control period (CONTROL_DT = 0.05 s, 20 Hz):
    1. read the encoders, turn them into measured (v, omega), predict the estimate
    2. every 2nd period (camera 10 Hz): render, detect ArUco markers, correct the estimate
    3. every 4th period (lidar 5 Hz): scan -> process_scan (walls, obstacles)
    4. the controller computes (v, omega) from the ESTIMATE, the latest lidar points and this frame's markers
    5. (v, omega) -> compensated wheel commands -> step MuJoCo 25 x 2 ms
- Ground truth isolation (the brief's constraint, enforced by design):
    - the controller is only ever passed estimator.x and sensor data;
    - the estimator starts from the configured START_POSE (its prior), not from the simulator;
    - ground truth goes only into the Log, used for the printed summary, the plots and the test scoring.
- Estimator interface shared by all estimators: predict(u, dt), update(observations), x, P. Dead reckoning runs
  alongside the EKF on the same odometry, for comparison only.
- The loop records the raw sensor stream (odometry per step, marker observations per frame), so filter settings
  can be replayed offline without re-running the simulation (used by test_estimation.py Part 3).
- main.run() takes keyword arguments that change the WORLD only (start offset, odometry errors, camera noise and
  calibration, lidar noise, missing markers, extra obstacles, a push) for the robustness trials (findings_E).

1.2 Mission (src/config.py)
- START_POSE (-1.5, -1.5, 0).
- WAYPOINTS (-0.6, -1.3), (-0.1, -0.7), (-0.05, 0.2), (0.1, 0.85), (0.5, 1.0), (1.0, 1.0), (1.1, 1.0): Anthony
  Fava's route through the middle of the room, ending at the pre-dock pose (1.1, 1.0) on the dock marker's normal
  with the camera ~0.6 m from the marker. The controller drives a cubic spline through it (findings_D 1).
- Clearance of the spline beyond the robot's radius (0.25 m): 8.8 cm from obstacles, 20 cm from walls; length
  4.36 m (outputs/control.txt Part 0).
- Then visual docking to 0.25 m camera-to-marker (findings_D 1.3).

1.3 Placeholder controller (kept as the baseline; python main.py --controller simple)
- Week 8 C.4: "point towards the next waypoint, drive and turn". omega = 1.5 x heading error,
  v = 0.15 cos(heading error), clipped at 0, so the robot turns on the spot when facing away.
  It slows approaching the final waypoint (v <= 0.5 x distance). No docking.
- Lidar safety stop: v = 0 if any lidar return lies in a corridor 0.41 m wide (chassis half width 0.153 + 0.05)
  out to 0.29 m ahead of the robot's origin (camera housing front 0.086 + 0.20).

1.4 First run, before odometry errors were added (ideal encoders, earlier mission)
- 4/4 waypoints in 38 s, 45 mm from the final waypoint, dead-reckoning error never above 9 mm.
- Lesson: after the caster fix, the MuJoCo wheels roll without slipping, so dead reckoning was unrealistically
  perfect and an EKF would have had nothing to correct. Hence section 2.


====================================================================================================
2. ODOMETRY ERROR MODEL IN THE SIMULATION (src/simulation/world.py, Encoders)
====================================================================================================
- The two classic error sources (Borenstein's UMBmark categories):
    systematic: each wheel's effective radius differs from the nominal 0.033 m the software assumes (tyre wear,
                load, manufacturing), by a different amount left and right, so the heading drifts
    random:     slip, a random walk on each wheel angle whose variance grows with the angle turned
- reported increment = true increment x (1 + scale_error) + N(0, slip_sigma^2 |increment|), then quantised to
  4096 ticks/rev. Errors accumulate.
- Defaults: SIM_WHEEL_SCALE_ERROR = (+0.8 %, -0.4 %) (left, right), SIM_WHEEL_SLIP_SIGMA = 0.02 rad/sqrt(rad).
- test_estimation.py draws new radius errors for every trial, uniform in +/-0.8 % per wheel.
- The robot's software never sees these values.


====================================================================================================
3. EKF DESIGN (src/estimation/estimation.py)
====================================================================================================
State x = (x, y, theta); built from the Week 7 C.3 ekf_predict / ekf_update and C.4 h_rb / H_rb.

3.1 Predict
- Exact-arc unicycle model f_uni and Jacobian F_uni (Week 7 C.4, src/control/model.py), driven by the encoder
  odometry (v, omega) measured over the last control period.
- Process noise (EXTENSION of Week 7, which used a constant Q_d): Q_d derived from the odometry error model.
  Each wheel's distance ds has variance
      (EKF_WHEEL_SCALE_SIGMA ds)^2 + EKF_WHEEL_SLIP_SIGMA^2 r |ds| + encoder quantisation,
  with EKF_WHEEL_SCALE_SIGMA = 1 % and EKF_WHEEL_SLIP_SIGMA = 0.02 rad/sqrt(rad). It is mapped onto the pose
  through the Jacobian of f_uni with respect to the two wheel distances (G Sigma G^T), then multiplied by
  EKF_Q_SCALE.
- Consequence: a stationary robot gains no uncertainty; a fast turn gains mostly heading uncertainty.

3.2 Update
- One ArUco range-and-bearing measurement at a time (sequential updates, Week 7 D.2), against the known marker
  map (cfg.MARKERS), using the covariance perception reports for that measurement, with the range and bearing
  variances scaled by EKF_R_SCALE.
- Bearing innovation wrapped (Week 7 C.5).
- EXTENSION: chi-square gate on the normalised innovation squared, NIS = nu^T S^-1 nu > 11.83 (2 dof, 99.7 %),
  to reject outliers such as a mis-identified marker (Week 8 discussion of bad data association).
- EXTENSION (added for criterion E, findings_E 2.1): lock-out recovery. If every marker measurement in a camera
  frame has been rejected for 5 frames in a row (0.5 s), the filter adds diag(0.3 m, 0.3 m, 30 deg)^2 to P and
  reprocesses the frame. It never fires in nominal missions (0 recoveries in 10/10 nominal trials).
- Covariance symmetrised after each update.

3.3 Prior: P0 = diag(0.05 m, 0.05 m, 3 deg)^2 around START_POSE.

3.4 Final tuning (src/config.py)
- EKF_Q_SCALE = 3.0
- EKF_R_SCALE = (5.0, 1.0)   (range variance x5, bearing variance x1)
- Reasoning in section 5.

====================================================================================================
5. TUNING: FROM OVERCONFIDENT TO CONSISTENT (the story for the report; EARLIER MISSION)
====================================================================================================
Measured on the earlier mission (placeholder controller, waypoints (1.2, -1.45), (1.2, 0.2), (1.2, 1.0),
(1.45, 1.0), ~38 s). The final-system sweeps in 4.1 confirm the conclusions on the current mission.

5.1 Starting point: Q x1, R x1 (first run of test_estimation.py)
- Accurate (RMS 4.3 mm) but OVERCONFIDENT: mean NEES 6.71; NEES under the 97.5 % bound on only 74 % of steps;
  2-sigma coverage position 69 %, heading 83 %; NIS 1.70; 29 updates rejected by the gate (a too-small P makes
  good measurements look like outliers).
- Week 7 D.4's knob, scaling Q_d, did not fix it on its own:
    Q scale   RMS pos    mean NEES   2-sigma pos   2-sigma heading   rejected
    0.1       32.2 mm    105.90       7 %          21 %              1218
    0.3        5.0 mm     17.62      36 %          54 %               181
    1          4.3 mm      6.71      69 %          83 %                29
    3          4.3 mm      5.07      83 %          91 %                24
    10         4.8 mm      4.55      88 %          91 %                23
  NEES stayed above 4.5 even at 10x, while NIS (each single measurement) looked fine. That pattern points at
  correlated measurement errors.

5.2 Diagnosis
- NEES split by state (Q x1, R x1): position 5.18 (expect 2), heading 2.02 (expect 1), so position is the main
  problem.
- Cause 1, Q too small: the wheel-radius error is a constant BIAS, but the noise model treats it as fresh random
  noise each step. Over N steps without a marker the real error grows like N, the model's standard deviation only
  like sqrt(N).
- Cause 2, correlated camera errors: at 10 Hz the camera sees the same marker from almost the same place each
  frame, with almost the same error (corner bias, calibration), so successive measurements are not independent
  and the filter over-counts them.
- Evidence: autocorrelation of the same marker's whitened innovations, k camera frames apart, on the earlier
  mission k=1 range +0.33 / bearing -0.01, k=2 +0.22 / +0.04, k=3 +0.14 / -0.01; on the final mission (4.1)
  +0.32 / -0.06, +0.20 / +0.01, +0.15 / +0.04. Range errors are correlated across frames; bearing errors are not.

5.4 Decision: Q x3, R range x5, bearing x1
- Q x3 covers the radius bias over the blind stretches between markers.
- Range x5 follows the correlated-measurement argument: errors correlated over ~n frames carry about 1/n of a
  frame's information each, so R_eff ~ n R. An autocorrelation still +0.14-0.15 three frames on supports n ~ 5.
- Bearing left alone, because its errors are independent; inflating it too made the filter more conservative
  for nothing.
- Accuracy is essentially unchanged by the tuning; consistency goes from NEES 6.7 to 2.7-2.9 (earlier and final
  missions).


====================================================================================================
6. CAVEATS AND POSSIBLE EXTENSIONS
====================================================================================================
- Mean NIS ~0.5 against an expected 2: with Q x3 the predicted covariance is generous right after each
  correction, so innovations look small. This is the price of covering the radius BIAS with white noise.
- Principled fix (High Distinction extension): augment the state with the two wheel-radius errors and estimate
  them (x = (x, y, theta, e_l, e_r)). Q could then return to x1, NIS should approach 2, and the filter would
  learn the robot's calibration. Compare against the current filter on the same recordings.
- The Q x3 tuning is for +/-0.8 % wheel errors; with +/-2.5 % (findings_E odometry_x3) the filter becomes
  overconfident (NEES 45) and relies on the lock-out recovery.
- Results above are for one route and one marker layout. Wrong priors, worse odometry, camera faults, missing
  markers and pushes are tested in findings_E.
